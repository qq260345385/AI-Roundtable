# AI Roundtable v0.8.0 决策简报设计

状态：已确认

日期：2026-07-16

目标版本：v0.8.0

## 1. 背景

AI Roundtable v0.7.0 已支持多模型三阶段会议、真实 Provider、联网 Evidence、本地资料、引用检查、Markdown 导出和浏览器本地历史。当前基线可通过 41 个测试文件、414 项测试、类型检查、lint 和生产构建。

下一版的主要问题不是继续增加搜索选项，而是让普通用户更快完成核心任务：输入议题、选择模型、开会，并在结束后得到清晰且可追溯的建议。

现有首页同时展示模型大卡片、圆桌席位、资料选项、简要模式、总结模型和历史会议，主操作不够聚焦。现有结果页默认停留在第三阶段的共识、分歧和下一步，缺少一句明确推荐、成立条件、置信度和推翻条件。MockProvider 的部分内容仍在建议未来增加已存在的用户输入与真实 Provider，也需要更新。

## 2. 已确认的产品决策

- 更新优先级：简化操作并突出最终决策。
- 判断强度：结果页主动给出明确推荐，而不是保持中立。
- 首页方向：采用“聚焦输入”布局。
- 结果页方向：采用“决策简报”布局。
- 低证据策略：仍给出暂定推荐，但必须标注低置信度、缺失证据和推翻条件。
- 实现深度：完成数据、生成、降级、展示、导出、历史和测试的纵向切片，不做只改界面的伪升级。

## 3. 目标

1. 用户无需理解全部设置即可开始一次会议。
2. 会议结束后，用户能在第一屏看到推荐、理由、成立条件、置信度和下一步行动。
3. 推荐必须保留可追溯性；原始发言、分歧、Evidence 和引用状态不能丢失。
4. 证据不足、模型分歧或部分 Provider 失败时，系统仍提供有用的暂定建议，但不能伪装成确定事实。
5. 旧版历史记录、现有 API 消费方和 Markdown 工作流保持兼容。

## 4. 非目标

v0.8.0 不加入以下内容：

- 账号、数据库、云同步或多人协作。
- 评价维度权重、方案打分、决策模板或追问向导。
- 新的搜索服务或对搜索核心的全面重写。
- Provider 配置管理界面。
- TypeScript、ESLint、Node 类型等大版本迁移。

这些能力需要独立验证用户需求，不与本次决策简报混合实施。

## 5. 用户体验

### 5.1 首页

首页第一视觉焦点是议题输入框和“开始圆桌”按钮。

- 已选模型显示为轻量标签，并允许进入选择界面调整。
- 默认沿用当前可用模型选择，不额外增加必填步骤。
- 联网搜索、本地资料、会议长度和总结模型统一进入“更多设置”，默认折叠。
- 模式与 Provider 状态保留必要提示，但不重复占用多个区域。
- 历史会议放在主操作之后。
- 不再用大面积圆桌席位和重复模型卡片同时表达同一信息。

### 5.2 会议进行中

保留现有三阶段会议过程和实时状态：

1. 独立观点
2. 自由回应
3. 共识整理

进行中不显示半成品推荐。只有最终总结经过规范化和质量门控后，才生成决策简报。

### 5.3 会议完成

会议完成后默认进入决策简报，而不是停留在第三阶段记录。第一屏按以下顺序展示：

1. 推荐结论
2. 推荐状态与置信度
3. 核心理由
4. 成立条件
5. 风险与主要反对意见
6. 缺失证据
7. 推翻条件
8. 一个明确的下一步行动

三阶段原始发言、模型观点变化、Evidence、引用状态、失败记录和开发者诊断保留在可展开详情中。普通用户默认看到结论，仍可按需追溯过程。

### 5.4 导出与历史

- Markdown 导出使用与结果页一致的“结论优先”层级。
- 新会议历史保存完整决策简报。
- v0.7.0 及更早的历史记录在读取时生成兼容简报，不回写或篡改原始浏览器数据。

## 6. 数据模型

在现有 `MeetingSummary` 中新增可选的 `decisionBrief`，原有字段继续保留：

```ts
type DecisionStatus = "firm" | "tentative" | "unavailable";
type DecisionConfidence = "high" | "medium" | "low";

type DecisionBrief = {
  recommendation: string;
  status: DecisionStatus;
  rationale: string[];
  conditions: string[];
  risks: string[];
  confidence: DecisionConfidence;
  evidenceGaps: string[];
  reversalConditions: string[];
  nextAction: string;
};
```

`decisionBrief` 在持久化与 API 边界上保持可选，以兼容旧数据；完成规范化后，前端消费的会议结果始终获得一个合法的决策简报视图。

## 7. 生成与数据流

### 7.1 总结生成

总结 Provider 同时输出现有会议总结和结构化决策简报。提示词要求：

- 必须给出一句清晰推荐。
- 推荐理由必须来自本轮有效发言与可用 Evidence。
- 不能把模型共识误写为外部事实。
- 必须显式给出成立条件、主要风险和推翻条件。
- 下一步只能保留一个近期、具体、可执行的动作。

MockProvider 使用当前产品能力生成与议题相关的演示内容，不再输出过时的开发路线建议。

### 7.2 规范化

新增独立的决策简报模块，负责：

- 类型校验与字段清洗。
- 长度限制、空值处理和数组去重。
- 从旧版 `consensus`、`differences`、`risks` 和 `nextSteps` 生成兼容视图。
- 为缺失字段提供保守且可解释的降级值。

该模块不放入 `evidence-pack.ts`，避免继续扩大搜索模块职责。

### 7.3 质量门控

现有 Evidence、引用和总结质量门控完成后，再计算最终推荐状态：

| 条件 | 状态 | 置信度约束 |
| --- | --- | --- |
| 有效模型充足、关键分歧可解释、证据支持主要事实 | `firm` | 可为高或中 |
| Low-Evidence Mode、严重分歧、部分 Provider 失败、关键引用降级 | `tentative` | 最高为中，通常为低 |
| 有效模型不足或总结完全不可用 | `unavailable` | 低 |

门控可以降级状态、补充缺失证据和推翻条件，但不能凭空提高置信度或制造外部事实。

### 7.4 实时会议

实时状态使用合法的空简报占位。最终总结完成前，前端只展示阶段进度；完成后一次性替换为经过门控的决策简报，避免中途结论反复变化。

## 8. 组件与模块边界

建议的职责边界：

- `src/lib/meeting/decision-brief.ts`：规范化、旧数据兼容、状态降级和展示视图生成。
- `src/lib/meeting/decision-brief.test.ts`：决策规则单元测试。
- `src/components/roundtable/DecisionBriefPanel.tsx`：只负责呈现决策简报。
- `MeetingRoom`：负责完成态与阶段态切换，不内嵌决策规则。
- `MeetingSetupView`：负责聚焦输入与折叠设置，不承担 Provider 或会议引擎逻辑。

实现时确认 `MeetingBoard`、`MeetingRecapPanel` 等当前未进入主流程的组件。能复用的合并为一个结果入口；确认无生产调用且测试迁移完成后再移除，避免两套结果页继续漂移。

本次只做服务于决策简报的定向拆分，不借机全面重构 `evidence-pack.ts`、搜索规划或会议引擎。

## 9. 异常与降级规则

- 总结缺少部分字段：从现有总结补齐，强制 `tentative`。
- 证据不足或引用无效：保留暂定推荐，将问题写入 `evidenceGaps`，置信度不得为高。
- 模型严重分歧：保留主要反对意见，并提供可观察的推翻条件。
- 部分 Provider 失败：保留成功结果，状态降为 `tentative`，说明缺席模型可能影响结论。
- 有效模型不足或总结失败：使用 `unavailable`，展示恢复建议，不伪造推荐。
- 旧历史缺少新字段：读取时生成低置信度兼容视图。

所有错误信息继续遵守现有脱敏规则，不暴露 API key、Authorization、Bearer、完整第三方错误体或内部堆栈。

## 10. 测试策略

### 10.1 单元测试

- 合法决策简报的规范化。
- 缺失字段补齐、长度限制和去重。
- `firm` 到 `tentative` 的降级规则。
- `unavailable` 的触发条件。
- 旧版会议结果兼容转换。
- Low-Evidence、无效引用、严重分歧和部分失败场景。

### 10.2 集成与回归测试

- MockProvider 与真实 Provider 总结解析。
- 普通会议与实时会议最终结果一致。
- API 路由返回新字段且保持旧字段。
- 历史记录保存、读取和旧格式兼容。
- Markdown 导出顺序、状态标签和缺失证据。
- 首页折叠设置不改变原有请求参数。

### 10.3 端到端与视觉验收

- Mock 模式快速开会：不展开高级设置即可完成会议并看到决策简报。
- 低证据或部分失败会议：显示暂定推荐、低置信度、缺失证据和推翻条件。
- 桌面与移动端检查首页和结果页。
- 长页面使用完整页面截图；必要时补充分段截图，避免只检查当前视口。

## 11. 依赖与发布边界

- 功能实现完成后，只升级兼容的补丁版本和明确的安全修复。
- 不在 v0.8.0 同时进行 ESLint、TypeScript 或 Node 类型的大版本迁移。
- 使用官方 npm registry 执行安全审计；当前镜像不支持 npm audit 接口，不能把镜像的 404 当成无漏洞。
- 更新 `APP_VERSION`、`package.json`、README、CHANGELOG 和设计说明中的版本与能力描述。
- 发布前运行 `npm run verify`；真实搜索 smoke test 仍保持手动、可选且不进入默认验证链路。

## 12. 验收标准

v0.8.0 必须同时满足：

1. 用户无需展开高级设置即可开始会议。
2. 完成页第一屏包含推荐、状态、置信度、成立条件和下一步。
3. Low-Evidence、严重分歧和部分失败不会显示为高置信度确定建议。
4. 原始发言、分歧、Evidence、引用状态和失败记录仍可追溯。
5. 旧版历史记录能正常打开。
6. Markdown 与界面使用一致的结论优先结构。
7. Mock 内容反映当前产品能力。
8. 所有现有测试继续通过，并增加决策简报相关覆盖。
9. 类型检查、lint 和生产构建通过。
10. 桌面和移动端完整页面视觉检查通过。

## 13. 实施顺序约束

实现计划应按“数据契约与回归测试 → 生成与降级 → 历史和导出 → 结果页 → 首页 → 端到端与发布”的顺序拆分。这样每一步都有稳定接口，避免先完成漂亮界面再倒推不可靠的数据语义。
